Checkpoint 13c · Search, menu, scan and lock

Your 13b notes, drawn in look A at true scale. The bar is now four pieces: menu on the left, a search bar, then the scan and lock circles on the right. The keyboard opens on a start page with your two most-used and two most-recent documents. The menu holds People, Documents and a Settings card. The keyboard shows no check status at all: failed checks are reviewed in the app (section 3).

Keyboard opens→Start page · 2 most used + 2 recent→Tap one, or search→Its keys→Scan circle to check · lock circle to lock
Typing a search inside a keyboard. iOS breaks a keyboard that puts a normal text box inside itself: once that box takes focus, the keyboard can no longer type into the form. This is why search was dropped in checkpoint 12. The way round it: the keyboard draws its own small A to Z pad, and those letters go into the search, never into the form. Frame 2 shows it. It costs a second set of keys to build, but it is safe.

Questions

Q1 · When a document is loaded, the search bar shows its name (frame 3), and tapping it searches again. Or should it always read “Search” and show the loaded document somewhere else? Recommended: show the name, so you always know whose document you are typing from.
Q2 · Start page each time the keyboard opens, or only when you have not used it within the lock window (otherwise you return to the keys you left)? Recommended: only after the lock window. Switching apps mid-form returns you to the same keys.
Q3 · Build the keyboard’s own letter pad for search (frame 2)? Recommended: yes. Without it, search can only be by tapping, as in the People list.
Q4 · Taking status off the keyboard entirely means the small green ✓ on verified keys goes too, not just failed checks. Recommended: yes, the keyboard only fills; the app judges.
Q5 · If you later edit a confirmed field to a new value that fails its check, flag it once more? Recommended: yes. It is new data, so it gets one new review; a confirmation is never undone otherwise.
